## 0. 决策依据：截图离线实验

定方案前，用 PC 上的 C# 原型（System.Drawing，单线程，未优化，脚本不进仓库）对 47 张实机截图和 59 个原始图标做了识别实验。数字只用于判断可行性，正式阈值在第 9 节第 2 步用 Kotlin 实现重新测量。

| 项目 | 结果 |
| --- | --- |
| 分辨率 | 47 张都是 2388×1080 |
| 槽位位置 | 逐像素方差分析：4 个槽位左上角 x = 1088 / 1251 / 1414 / 1577，y = 248，各 90×90 px，间距 163，所有截图一致 |
| 其他元素（10 px 粗定位） | 标题约 x 1250–1540、y 132–180；刷新按钮长条约 x 1070–1700、y 384–480，循环箭头中心约 (1380, 432)；开关约 x 1320–1440、y 588–636 |
| 面板位置 | 槽位中心线 x≈1377，屏幕中心 x=1194。面板不在正中，布局不能假设居中 |
| 稳定锚点 | 标题区域（含骰子）在 47 张图之间最大差异 21.3，刷新按钮区域是 41.7（开关开/关时按钮外观可能不同，原因未确认）。标题文字会随游戏语言变化，所以最终选骰子图标做锚点（第 3.1 节） |
| 匹配方法 | 图标原图缩放后只比较不透明像素（alpha ≥ 200）的 RGB 平均绝对差（0~255），在 ±4 px 内取最优偏移 |
| 图标显示尺寸 | 出现过的 50 个图标里 47 个在游戏中长边约 90 px；「好运气」「天赋异禀」约 88 px；「武器重铸」约 76 px（按 90 px 匹配距离 31.8，按 76 px 降到 9.8）。所以每个因子要按自己的显示尺寸生成模板 |
| 正确匹配距离 | 按各自尺寸匹配后约 3~23 |
| 区分度 | 统一按 90 px 匹配时，除「天赋」系列和「武器重铸」外，最优与次优至少差约 29；「武器重铸」差 19（按 76 px 匹配后最优距离降到 9.8，次优未重测）。「天赋位置+1」与另外两个约差 14。**「天赋选择+1」与「天赋自助餐」只差 2~3**（两张图标彼此距离 3.8），而第 3 槽两者都可能出现 |
| 问号状态 | 7 张问号截图的 4 个槽位像素完全一致（距离 0.0），与所有因子图标距离 ≥ 35.7 |
| 覆盖率 | 40 张已刷新截图只有 27 种组合、50 个因子。未出现的 9 个：脆皮、武器过热、亢奋的敌人、无知觉、全面戒备、跟踪激光、箱子突变、跑起来的敌人、复活苏生 |
| 速度 | 59 模板 × 25 偏移，每槽约 82 ms（含 JPEG 解码）。按第 3.2 节剪枝后会明显下降，需在手机上实测 |

答案草稿 `app/src/androidTest/assets/screenshots/labels_draft.csv` 是原型的输出。已用 17 种组合和 11 组冲突校验，40 行全部合法，但仍须维护者肉眼核对，否则测试就成了识别器自己验证自己。

## 1. 第 5 节问题的结论

### 1.1 截图方案（5.1）

结论：**两种截图都要支持，用同一个 `ScreenCapturer` 接口隔开。先交付无障碍截图；MediaProjection 作为「高速模式」放在第 9 节第 7 步，等真机数据出来再决定做不做。** 频率设置保持 1~10 次/秒，不下调，界面上显示当前截图方式实际能达到的上限。minSdk 保持 26。

| | 无障碍截图 `takeScreenshot()` | MediaProjection（录屏） |
| --- | --- | --- |
| 系统版本 | API 30+（Android 11） | API 21+ |
| 频率 | AOSP 源码里两次调用的最小间隔常量是 333 ms[^a11y]，约 3 次/秒。各版本和厂商 ROM 是否相同未查证，必须真机实测 | 跟随屏幕刷新，没有这个限制 |
| 授权 | 开启一次无障碍服务，长期有效 | 每次开始都要用户点同意；Android 14 起一次同意只能用一次[^mp] |
| 额外负担 | 无 | 必须运行 `mediaProjection` 类型的前台服务并显示常驻通知；Android 15 QPR1 起状态栏有醒目的录屏标记，锁屏会自动停止[^mp] |

理由：

- 点击只能靠无障碍服务的 `dispatchGesture`，所以无障碍服务无论如何都要开。截图也用它，用户只需授权一次。
- 3 次/秒是否够用可以估算：「无限能量 + 特卖日」期望约 584 次，3 次/秒约 3.3 分钟，10 次/秒约 1 分钟。游戏本身能否每秒处理 10 次刷新也还不知道。先拿到真机数据，再决定是否多维护一条截图路径。
- minSdk 不需要为截图调高。Android 8~10 的设备照样能用配方管理，「自动刷新」入口提示需要 Android 11 及以上；做了高速模式后，这些设备也能用。

### 1.2 识别技术（5.2）

结论：**不引入 OpenCV，用纯 Kotlin 实现「带透明掩膜的像素差模板匹配」。模板由 `assets/factors/icons/` 里的图标原图在开始刷新前缩放生成并缓存；`res/drawable` 那份继续给界面用，两份都保留。**

- 第 0 节的实验表明，最朴素的逐像素比较就能把绝大多数图标拉开约 29 的差距，难点只集中在「天赋」系列。OpenCV 在这里没有提供必需的能力，反而要打包 native 库（体积大，需要按 ABI 拆分 APK），也不能直接在纯 JVM 单元测试里运行。Maven Central 上 `org.opencv:opencv` 当前最新版本是 5.0.0.1（已查证[^opencv]），留作识别不够用时的后备。
- 模板不从截图裁取。有 9 个因子从没在截图里出现过，裁不出来。原图带透明通道，正好当掩膜用，只比较图标本身的像素，不受槽位背景影响。
- 个别图标在游戏里显示得更小（「武器重铸」长边约 76 px，多数约 90 px），所以每个因子有自己的缩放系数，默认 1.0，实测值写在代码里的覆盖表中（第 3.2 节）。
- 界面锚点（标题旁的「?」帮助图标，原称「骰子」，见第 3.1 节 2026-11-02 修订）和 4 个问号模板只能从实机截图裁出，放在 `app/src/main/assets/recognition/`。它们同样是凉屋的美术资源，见第 10 节第 4 条。

### 1.3 模块边界（5.3）

结论：**新建纯 Kotlin JVM 模块 `core-engine`，放识别算法和刷新状态机；`app` 只负责 Android 系统对接（截图、点击、悬浮窗、权限）。**

```
app ──► core-engine ──► core-domain
 │                        ▲
 └────────────────────────┘
```

- 不放进 `core-domain`：`core-domain` 是规则与数据，识别和状态机是另一类职责，还会引入协程依赖。分开以后两个模块的测试互不干扰。
- 不放进 `app`：放在 `app` 里只能用仪器测试，必须连手机才能跑。放在 JVM 模块里，`.\gradlew.bat :core-engine:test` 在电脑上几秒就能跑完 47 张截图。
- 图片在 `core-engine` 里统一表示为 `ArgbImage(width, height, pixels: IntArray)`，不依赖 Android 的 `Bitmap`。缩放和裁剪也用纯 Kotlin 实现，这样电脑上的测试和手机上运行时生成的模板逐像素一致。
- 状态机通过 3 个接口和外界打交道，测试时换成假实现：

| 接口 | 作用 | app 中的实现 | 测试中的假实现 |
| --- | --- | --- | --- |
| `ScreenCapturer` | 取一帧画面，并报告最小截图间隔 | `A11yScreenCapturer` | 按顺序返回截图文件 |
| `Tapper` | 在屏幕坐标点击一次 | `GestureTapper` | 记录点击坐标 |
| `FactorRecognizer` | 一帧 → 4 个槽位结果 | （就在 core-engine 里） | 可直接用真实现 |

### 1.4 测试策略（5.4）

结论：**47 张截图全部用于 `core-engine` 的 JVM 单元测试；仪器测试暂不写，真机部分靠第 9 节里的手动验证步骤。**

- 截图从 `app/src/androidTest/assets/screenshots/` 移到 `core-engine/src/test/resources/screenshots/`，因为它们只给识别测试用。
- 图标继续只保留 `app/src/main/assets/factors/icons/` 一份。测试通过 Gradle 传入的系统属性读取这个目录，不复制。
- 答案文件 `labels.csv`，与截图放在一起，格式：`file,slot1,slot2,slot3,slot4`。值用因子 `key`（比 id 好核对），问号状态写 `?`。测试启动时通过 `factors.json` 把 key 换成 id，未知 key 直接报错。
- 由维护者核对 `labels_draft.csv`，确认无误后改名为 `labels.csv`。
- 测试分 4 类：
  1. **逐张答案测试**：每张截图 4 个槽位的结果必须等于答案。
  2. **阈值报告**：打印所有正确匹配的最大距离和最小差距，作为调整阈值的依据。
  3. **模板可分性**：59 个模板两两比较。这一项也覆盖了截图里没出现过的 9 个因子。
  4. **合成分辨率**：把截图缩放、加黑边，模拟其他分辨率，验证校准（第 3.1 节）。
- 目前缺少「不是因子界面」的截图，这类负样本要请维护者补拍（第 10 节）。

### 1.5 交互细节（5.5）

| 问题 | 结论 | 理由 |
| --- | --- | --- |
| 命中提醒 | 悬浮窗展开并高亮 4 个因子，同时短震动（可在设置里关闭）。不发通知，不放声音 | 命中时玩家正看着屏幕。通知在 Android 13+ 要额外申请运行时权限；联机时玩家常开语音，声音容易打扰 |
| 识别失败 N | **N = 3**。任一槽位 UNKNOWN、或 4 个结果不符合 17 种组合/冲突规则时，**不点刷新**，重新截图；连续 3 帧仍失败就暂停 | 看不懂的画面绝不能刷掉，否则可能把玩家想要的组合刷没。不点击时画面不变，重试只用来排除偶发的截图问题，3 次足够 |
| 刷新无效 | 点击后连续 3 轮识别出完全相同的 4 个因子，判定点击没生效并暂停 | 合法刷新连续 3 次相同的概率可以忽略 |
| 总次数上限 | 需要。默认值 = 期望次数 × 3（至少 100），用户可改或关闭 | 按 `ProbabilityCalculator` 的等概率假设，约 95% 的情况会在上限内命中（1 − e⁻³）。等概率假设未经验证 |
| 默认频率 | 3 次/秒 | 与无障碍截图的上限一致 |

## 2. 模块与包结构

## 3. 识别算法

### 3.1 自动校准（没有位置档案或快速核验失败时做，见第 3.4 节）

目的：求出当前屏幕相对参考截图（2388×1080）的缩放系数 `scale` 和面板偏移 `(originX, originY)`。之后所有坐标都按 `参考坐标 × scale + origin` 换算。

> **2026-11-01 修订**：原方案的副锚点「循环箭头」作废。主力开发的锚点测量（`AnchorSurveyTest`）发现，开关关闭时刷新按钮是禁用状态，箭头平均色 #2E343E，和背景 #222631 只差约 12，测不出来。改为「帮助图标粗定位 + 面板边框精修」，依据见调研报告实验 8。
>
> **2026-11-02 修订**：主力开发的实测（`docs/REPORT_DICE_LOCATE.md`）发现两个问题，第 1 段按下述修改。文档里原来叫「骰子」的锚点，实际上是标题「挑战因子」右边的白色「?」帮助图标，下面统一改称「帮助图标」。

校准分两段：先用帮助图标找到大概的缩放和位置，再用因子面板的边框把缩放和位置量准。所用元素在开关开、关两种状态下像素完全相同（47 张截图 std 都是 0）。

**第 1 段：帮助图标粗定位**

1. 初始猜测 `scale = 屏幕高度 / 1080`。
2. 帮助图标模板：参考坐标 x 1475..1507、y 125..162（33×38），从 `disable01.jpg` 裁出，存入 `assets/recognition/help.png`（原 `dice.png`，改名）。
3. 在 `scale × 0.80~1.20`（步长 0.02）范围内搜索：先在 1/4 分辨率下搜全屏，再在原分辨率下精修 ±4 px。
4. **同一屏上有 3 个外观相同的帮助图标**（2026-11-02 主力开发核对坐标发现，架构设计方用像素距离补测印证，2026-11-03 维护者看图确认）：
   - (1475, 125)：「挑战因子」标题右侧，真锚点。
   - (2127, 125)：「周挑战」标题右侧。
   - 约 (1952, 740)：下方手枪图标的右侧。

   粗搜只保留 1 个位置时，1/4 分辨率下图标只剩约 8×10 px，3 个图标的距离只差 0.5，背景的细微差别就决定了谁排第一，实测 5 组里有 3 组选错（详见调研报告实验 12）。
5. **改为保留多个候选**：粗搜保留距离最小、互不重叠的前 K = 5 个位置，每个都在原分辨率下精修，按距离排序后依次交给第 2 段。取第一个通过残差检查和槽位验证的结果。假锚点周围没有面板竖条，第 2 段会因为找不到边或残差超标把它拒掉，所以「校准出错就停下、不用错误坐标」的性质不变。K = 5 是因为同屏已知 3 个，留 2 个余量给噪声造成的假匹配。
6. **`s0` 的精度按图标宽度分档**（2026-11-02 实测）：图标只有 33 px 宽，画面缩小时模板尺寸每差 1 px，缩放就差约 3%（缩放 0.5 时约 6%）。实测缩放 0.5 时位置是对的，但 `s0` 误差有 −5%，超过原来的 ±3%。
   - 图标宽度 ≥ 25 px（缩放约 0.75 以上）：`s0` 误差应 ≤ 3%。
   - 图标宽度 < 25 px：`s0` 误差应 ≤ 6%。
   - 第 2 段的搜索窗口相应放宽：由「0.04 × s0 × |参考 x − 1475| + 6」改为「**0.06** × s0 × |参考 x − 1475| + 6」。实验 8c 里窗口放到 15% 才出现错配，6% 在安全范围内。
7. 帮助图标只用来缩小第 2 段的搜索范围，不直接换算槽位。

**不采用的方案**（记录在此，避免以后重复讨论）：用两个帮助图标的间距求缩放。缩放 0.5 时 2 px 的位置误差只带来约 0.6% 的缩放误差，精度更好，但要依赖「周挑战」面板始终存在、两个面板的相对位置不变。周挑战未开放、活动期间等情况下是否成立没有证据，而方案 5、6 不增加任何依赖。

**第 2 段：面板边框精修**

面板左右两侧各有一条比面板底色亮约 11 个亮度级的竖条（平均亮度 34 → 45），宽约 40 px。找边只看「哪里跳变」，不看跳变后的绝对亮度，所以对设备之间的亮度、对比度差异不敏感。两侧最外的边相距 823 px，用来测缩放误差很小。

坐标约定：边缘和槽位坐标统一按「像素边界」换算，即像素下标 i 的左边界是 i，`屏幕 = origin + scale × 参考` 只对边界成立。表里写的是「跳变后第一个像素」的下标，它正好等于跳变处的边界坐标。PC 原型没有严格区分这一点，误差仍 ≤ 0.5 px；Kotlin 实现请统一按边界写，并在单元测试里覆盖 scale ≠ 1 的情况。

| 用途 | 参考位置（跳变后第一个像素） | 方向 | 求剖面的位置（参考坐标） |
| --- | --- | --- | --- |
| 横向缩放和 X 偏移 | x = 966、1006、1747、1789 | 升、降、升、降 | 对 y 200..660 每 4 行求平均，跳过刷新按钮所在的 y 370..505 |
| Y 偏移 | y = 236、350（槽位外框上沿、下沿）、690（面板下边框） | 升、降、升 | 对槽位外框内侧的列（x 1083..1086、1180..1183、1572..1575、1669..1672）和面板空白列（x 1012..1050、1702..1740）求平均 |

步骤：

1. **横向**：按 `s0`、`ox0` 预测 4 条竖边的位置，在「预测位置 ± (0.06 × s0 × |参考 x − 1475| + 6)」内找符号正确、梯度最大的点（梯度取「后 2 px 之和 − 前 2 px 之和」的一半，再做抛物线插值到亚像素）。4 个点对 `x_屏 = ox + s × x_参` 做最小二乘，得到 `s` 和 `ox`。窗口系数 2026-11-02 由 0.04 改为 0.06，原因见第 1 段第 6 条。
2. **纵向**：`s` 已知，按 `oy_pred = dy − s × 125` 预测 3 条横边，在 ± 8 px 内找边，`oy` 取 3 个点的平均。
3. **搜索窗口的取舍**：窗口按「`s0` 误差最多 6%」设计（2026-11-02 由 4% 放宽，见第 1 段第 6 条）。窗口放宽到 15% 时，槽位外框和面板内部的其他边缘会落进窗口，被错当成面板边框，拒收率明显上升。所以第 1 段必须保证 `s0` 误差在第 1 段第 6 条的分档范围内。这一条要在 Kotlin 的合成测试里单独断言。
4. **残差检查**：横向和纵向的最大拟合残差都必须 ≤ 1.5 px。纵向残差同时检验了「横竖缩放一致」，因为 236 到 690 之间有 454 px，缩放差 1% 就会产生约 4.5 px 的残差。
5. 不用面板上边框（y 84）。enable33、39、40 中面板上方 y 60..90 一带有内容变化，用了它会把槽位位置拉偏 7 px。

**验证与重试**

- 按结果算出 4 个槽位，每个槽位必须要么像问号，要么能匹配到某个因子（原第 3 条，保留）。
- 残差检查或槽位验证不通过时，换下一帧重试，最多 3 帧。3 帧都失败就暂停并提示「请确认停在挑战因子界面」。
- 结果按「截图宽 × 高」缓存在内存里。截图尺寸变化（旋转、分屏）时重新校准。

**合成测试结果**（PC 原型，全部 47 张截图，按上面的窗口；详见调研报告实验 8、12）：缩放 0.5~1.33 倍、加黑边、JPEG 质量 50~85、加随机噪声，`s0` 误差 ±6% 以内、帮助图标位置误差 ±2 px 时，通过残差检查的结果槽位误差都 ≤ 0.40 px。最重的噪声组合（JPEG 50 加强噪声）下 1 帧被拒收。`s0` 误差到 ±8% 时 47 帧全部被拒收。在做过的所有组合里，**没有出现过「槽位误差超过 2 px 却通过残差检查」的结果**。

**自动校准覆盖不了的情况**：上面的合成测试只模拟了「整体等比缩放」。如果面板被横向拉伸，或者游戏改版后面板换了布局、换了边框，自动校准会因为残差超标而失败（不会刷错）。这些情况交给第 3.4 节的手动引导。

注意：第 2 段纵向剖面取的列 x 1083..1086 等，是按实验 8 当时的方框坐标定的。实验 11 发现方框竖边实际在 1076/1190 等处（第 3.4.4 节），这些列其实落在方框内侧 7~10 px，在方框上沿、下沿处照样能测到跳变。实验 8 的合成测试就是用这组列跑出来的，所以**按原样实现即可，不要改**；改动后需要重跑合成测试。

只有一台测试机，多分辨率只能靠合成测试验证算法本身。真实设备上的表现要等用户反馈，所以悬浮窗要提供「保存当前画面」按钮，方便用户提交问题。

### 3.2 槽位匹配（每帧 4 次）

**模板生成**（校准后一次性完成，缓存在内存）：

- 图标原图按「长边 = 90 × scale × 尺寸系数」缩放，居中贴到槽位大小的透明画布上。缩放用纯 Kotlin 的面积平均算法，测试和运行时结果一致。
- 尺寸系数默认 1.0。实测覆盖值：`reforge_weapon` 0.84、`good_luck` 0.98、`exceptionally_talented` 0.98。截图中没出现过的 9 个因子暂用 1.0，属于**未验证**，需要真机遇到时补测。
- 缩放后 alpha ≥ 200 的像素作为掩膜，只比较这些像素。

**候选剪枝**：每个槽位只比较 `Factor.canAppearInSlot()` 允许的因子。第 1~4 槽分别是 28、37、39、16 个，合计 120 次比较，原来是 236 次。

**距离**：掩膜内像素 RGB 三通道平均绝对差，范围 0~255。偏移搜索分两轮：所有候选在 ±2 px（步长 2）内搜索，距离最小的 3 个再在 ±3 px（步长 1）内精修。

**判定**（第 9 节第 2 步已用 Kotlin 实现实测，初值全部保留，见下方「实测依据」）：

| 条件 | 结果 |
| --- | --- |
| 与该槽问号模板距离 < 10 | `Question` |
| 最优距离 ≤ 30，且次优 − 最优 ≥ 8 | `Factor(id)` |
| 最优距离 ≤ 30，差距不足，但二次比较中胜者对每个对手的优势都 ≥ 8 | `Factor(id)` |
| 最优距离 ≤ 30，差距不足，二次比较也分不开 | `Ambiguous(候选 id 集合)`，集合里放距离在最优 + 8 以内的因子 |
| 其他 | `Unknown` |

**实测依据**（2026-11-01，scale = 1，47 张截图共 160 个因子槽位、28 个问号槽位；报告由 `ThresholdReportTest`、`TemplateSeparabilityTest` 生成，位于 `core-engine/build/reports/recognition/`）：

| --- | --- | --- | --- |

| 最小差距（不含「天赋选择+1 / 天赋自助餐」） | 12.24（`buff_choice_plus1` 对 `buff_slot_plus1`） | `minGap` 8 | 4.2 |

| 二次比较的最小优势 | 截图 56.91，合成背景 72.32 | `secondaryMinGap` 8 | 48.9 |

| 因子槽位与问号模板的最小距离 | 21.38（`enable15` 第 4 槽 `good_luck`） | 同上 | 11.4 |

结果：188 个槽位全部识别正确，没有 `Ambiguous`。纯色背景合成测试中，59 个模板都能识别为自己，只有「天赋选择+1 / 天赋自助餐」这一对需要二次比较。两张模板的距离是 3.58，排第二近的一对是 13.79（`buff_choice_plus1` / `buff_slot_plus1`）。

实现说明：二次比较只用「两者都不透明且平均通道差 > 40」的像素，差异像素不足 30 个时视为分不开。「只有一方不透明」的像素没有使用，因为另一方在该位置的预期颜色是未知的槽位背景，算不出可比的距离。实测不需要它。以上数据只覆盖 scale = 1，第 3 步做完校准后要在合成分辨率下复测。

2. 就算二次比较还是分不开，也不一定要停。`Decision` 会把每个 `Ambiguous` 槽位展开成所有可能的组合，先去掉违反 17 种组合或冲突规则的组合，再逐个用配方判断。如果所有可能都是「未命中」，照常刷新；都是「命中」，照常停下；只有结论不一致时才算识别失败。配方里没有勾选这两个因子时，它们分不分得清对结果没有影响。

### 3.3 画面状态（每帧判断）

> **2026-11-01 修订**：维护者确认，问号截图（`disable*`）是「挑战因子开关关闭」的状态。开关关闭时刷新按钮被禁用，点了也不会刷新。原来的 `UNREFRESHED` 拆成按开关判断的两个状态。

- `FACTOR_SCREEN_ON`：面板边框残差和槽位验证通过，开关为开。正常识别 4 个槽位。
- `FACTOR_SCREEN_OFF`：面板边框残差和槽位验证通过，开关为关，且 4 个槽位都是问号。只和问号模板比较，不做因子匹配，不点击。
- `NOT_FACTOR_SCREEN`：校准失败（面板边框找不到或残差超标），例如切出游戏、弹出对话框或通知栏被拉下。

> **2026-11-02 修订**：原来用帮助图标（当时叫骰子）的匹配距离判断「是不是因子界面」。实测同一屏上就有 3 个外观相同的图标（第 3.1 节第 1 段第 4 条），游戏的其他界面也可能有同款图标，它的区分力不够。改为以第 2 段的**面板边框残差检查和槽位验证**为主证据：假锚点周围没有面板竖条，校准会失败。帮助图标的匹配距离只作为辅助证据，距离过大时可以提前判定为 `NOT_FACTOR_SCREEN`，省掉后面的搜索。

T_anchor 初值 45（47 张因子界面截图中，包含帮助图标的标题区域最大差异是 21.3；只取帮助图标后的数值在第 3 步重测）。现在没有「非因子界面」的截图，这个阈值还不能验证，需要维护者补拍负样本（第 10 节第 2 条）。

**开关判断**：开关打开时，滑轨左半段变成绿色。47 张截图的组平均色（参考坐标）：

| 采样点 | 开关关（7 张） | 开关开（40 张） |
| --- | --- | --- |
| (1325, 612)、(1350, 612)、(1340, 600) | #424A5D | #4DB022 |
| (1400, 612)、(1425, 612)、(1410, 625) | #2D333F | #424A5D |

判断方法：取参考区域 x 1320..1355、y 600..620（换算到屏幕坐标），统计「G 比 R、B 都大 40 以上」的绿色像素占比，> 50% 为开，< 10% 为关，介于两者之间按 `NOT_FACTOR_SCREEN` 处理（可能是开关正在切换的动画，或者画面被遮挡）。两个阈值是初值，第 3 步在 Kotlin 测试中按 47 张截图实测确认。

**问号只在开关关闭时出现**（维护者 2026-11-01 确认）：开关一打开，游戏立刻刷新一次，槽位直接显示 4 个因子，不存在「开关开 + 问号」的状态。因此：

- 问号模板仍然保留，但用途变了：只作为 `FACTOR_SCREEN_OFF` 的**辅助证据**（开关判断为关 且 4 个槽位都是 `Question`，两者一致才判定为关）。两者不一致时按 `NOT_FACTOR_SCREEN` 处理。
- `FACTOR_SCREEN_ON` 下如果某个槽位识别成 `Question`，说明画面异常（例如开关正在切换的过渡帧），按 `UNCERTAIN` 处理：不点击，重新截图，计入识别失败次数。

### 3.4 位置设置：自动校准为主，失败时手动引导（2026-11-01 新增）

> 维护者 2026-11-01 选定：自动校准为主，失败时进入手动引导；手动引导只让用户做两件事（拖 4 格轮廓、点一下刷新按钮）；确认预览在第一次设置和每次因出错重新设置时都要做。依据见调研报告实验 10、11。

**目标**：让工具扛住「布局变化」（分辨率、宽高比、面板被拉伸、游戏改版后面板挪位置或换边框）。扛不住「美术变化」（因子图标换了画法、新增因子），那些仍需要更新 `factors.json` 和图标。

#### 3.4.1 位置档案（CalibrationProfile）

设置成功后保存一份「位置档案」，之后每次开始都直接用它，不再每次校准。

| 字段 | 内容 |
| --- | --- |
| `screenWidth`、`screenHeight` | 截图尺寸，作为档案的键。尺寸变了（旋转、分屏、换设备）就当作没有档案 |
| `scaleX`、`scaleY`、`originX`、`originY` | 参考坐标到屏幕坐标的换算：`屏幕 x = originX + scaleX × 参考 x`，y 同理。**横纵缩放分开存**，自动校准得到的两个值相等，手动引导可以不等 |
| `tapX`、`tapY` | 刷新按钮的点击位置（参考坐标）。自动校准用内置值 (1377, 433)；手动引导用用户点的位置，按上面的换算反算回参考坐标后保存 |
| `toggleOnPatch` | 开关区域在「开」状态下的像素块，设置时从用户自己的屏幕截下（见 3.4.4） |
| `source` | `AUTO` 或 `MANUAL`，只用于日志和「保存当前画面」的问题报告 |
| `createdAt` | 设置时间 |

存在新的 DataStore 文件 `calibration_profile` 里，`toggleOnPatch` 按 PNG 编码后转 Base64 存，大小约几 KB。每种截图尺寸只保留一份。

`Calibration` 类相应改成 `scaleX`、`scaleY` 两个缩放。第 3.1 节的自动校准仍然只求一个缩放，结果同时填进两个字段。

#### 3.4.2 什么时候做什么

```
点击开始
  │
  ├─ 有当前截图尺寸的档案 ──► 快速核验（3.4.5）──通过──► 直接开始刷新（不打扰用户）
  │                                 │失败
  │                                 ▼
  └─ 没有档案 ─────────────────► 自动校准（3.1）──成功──► 确认预览（3.4.6）
                                    │失败（3 帧都不过）           │用户点「不对」
                                    ▼                             ▼
                                 手动引导（3.4.3）◄─────────────────┘
                                    │
                                    ▼
                                 确认预览 ──「对」──► 保存档案，开始刷新
```

- 快速核验失败时，先自动校准一次，不直接让用户手动操作。快速核验失败最常见的原因是玩家没停在因子界面，这时自动校准也会失败，弹出的提示是「请确认停在挑战因子界面、开关已打开」，并附带「手动设置位置」按钮。玩家不需要每次都重新框选。
- 悬浮窗设置里提供「重新设置位置」入口，玩家可以随时主动进入手动引导。
- 运行中如果连续识别失败暂停（第 1.5 节的 N = 3），暂停提示里也放「重新设置位置」按钮，但不自动进入。识别失败不一定是位置不对，也可能是被遮挡。

#### 3.4.3 手动引导

用户只做两件事：

1. **拖 4 格轮廓**：悬浮窗铺满屏幕，底层显示一张刚截的游戏画面，上面画一条「4 个等大、等间距的方框」轮廓。用户拖动它、拉它的左右两端，让它大致盖住游戏里的 4 个槽位方框。只需要拉左右两端：轮廓的高度跟着宽度按参考比例变化，纵向缩放交给吸附去测。初始位置放在「按屏幕高度等比换算的参考位置」，多数设备上一开始就八九不离十。
2. **点一下刷新按钮**：点在刷新按钮上，记下点击坐标。这个坐标只用来点击，不参与吸附。

用户松手后立刻吸附（3.4.4），把吸附后的轮廓画回屏幕，用户能看到它「跳」到了方框边上。吸附失败时轮廓变红，提示「没对准，请把框拖到 4 个方格上再试」，不进入确认预览。

注意：

- 引导期间的截图里会带着悬浮窗。手动引导的流程是「先截一张干净的图，冻结显示在悬浮窗底层，用户在截图上拖框」，不是在实时画面上拖。截图时悬浮窗先隐藏。
- 开关必须是开的。进入手动引导前先提示「请先打开挑战因子开关」，因为确认预览要用 4 个因子来验证。

#### 3.4.4 吸附算法（Snapper）

只假设「4 个等大、等间距的方框」，不使用帮助图标和面板边框，所以面板换了样式也能用。

槽位外框的形状（参考坐标，像素边界）：

| 边 | 位置 | 有效范围 |
| --- | --- | --- |
| 竖边（左沿升、右沿降） | x = 1076/1190、1239/1353、1402/1516、1565/1680 | y 244..344（方框四角有约 5 px 的倒角，避开） |
| 横边（上沿升、下沿降） | y = 236、350 | 每个方框的 x (左沿 + 9)..(右沿 − 9) |

注意：这组坐标是方框**最外圈**的边界。第 0 节和实验 8 里的 1081/1185 等是倒角处（y 236..243）的位置，不是竖边本身。

梯度：边界 t 处的跳变 = (p[t] + p[t+1] − p[t−2] − p[t−1]) / 2，再**截断到 ±8**。截断是关键：图标内部的边缘对比度高达 100 以上，不截断时会主导得分，把轮廓吸到图标上。方框边缘的跳变是 18，截断到 8 后每个采样点贡献相同，得分就变成「有多少采样点落在正确的边上」。

步骤（`ux` 为用户框给出的初值）：

1. **竖边搜索**：只看 8 条竖边，搜 `scaleX`（用户框推算值 ±12%，步长 0.5%）和左沿位移（±40 px，步长 1）。
2. **横边搜索**：固定 `scaleX`、`originX`，只看 8 条横边，搜 `scaleY`（`scaleX` × 0.75..1.33，步长 0.5%）和上沿位移（±40 px，步长 1）。分两步搜是因为横纵放在一起搜时，在面板被拉伸的情况下会吸到错误位置（调研报告实验 11 第 2 轮）。
3. **联合精修**：16 条边一起，`scaleX`、`scaleY` 各 ±1%（步长 0.25%），偏移 ±2 px（步长 0.5）。
4. **逐边检查**：对 16 条边分别统计「符号正确且幅度 > 4 的采样点占比」，**每一条边都必须 ≥ 0.9**，否则吸附失败。只看总分会漏掉「吸到相邻槽位上，大部分边都对、有一条边落空」的情况。

实验 11 的结果：用户框误差 ±10~30 px、面板被横向拉伸到 0.9~1.2 倍时，吸附结果的槽位误差都 ≤ 1.46 px，**没有错误结果通过逐边检查**。代价是在重压缩、强噪声的画面上拒收率较高（最重的一组 47 帧里拒收 24 帧），失败时让用户把框再对准一点重试就行。

#### 3.4.5 快速核验（有档案时）

每次点开始时用档案做一次快速核验。它不做任何搜索，只在固定位置比较像素，计算量远小于校准（耗时未实测）：

1. **开关区域**：用档案换算出开关区域（参考 x 1316..1439、y 592..627），和 `toggleOnPatch` 比较平均像素差。47 张截图里，「开」和「开」的距离是 0.00，「开」和「关」的距离是 40.89。阈值初值 15。
2. 距离 ≤ 15：认为是因子界面且开关开，进入正常刷新。第一帧识别时，4 个槽位必须都能匹配到因子（不能是 `Unknown`），否则视为核验失败。
3. 距离 > 15：可能是开关关闭，也可能不在因子界面。再用档案位置检查 4 个槽位是否都是问号：都是问号则判定为「开关关闭」并提示打开；不是则核验失败，走第 3.4.2 节的流程。

用用户自己屏幕上截下的开关做参照，有两个好处：游戏改版后开关换了颜色也能用；仓库里不需要内置开关的参考像素。第 3.3 节的「绿色像素占比」规则保留，作为**没有档案时**（自动校准阶段）的判断方法。

#### 3.4.6 确认预览

自动校准成功或手动引导吸附成功后，悬浮窗显示：

- 截图上 4 个槽位的位置（画框）。
- 每个槽位识别出的因子图标和中文名。
- 「对」「不对」两个按钮。

用户点「对」才保存档案。点「不对」进入手动引导（如果本来就在手动引导，就回到拖框那一步）。

强制预览的时机（维护者确认）：

- 第一次设置位置。
- 每次因出错而重新设置（快速核验失败后的自动校准、手动引导、用户主动点「重新设置位置」）。

有档案且快速核验通过时不弹预览。

预览时如果有槽位识别成 `Unknown`，不显示「对」按钮，只显示「不对，重新设置」。这样能保证保存下来的档案至少认出过一次完整的 4 个因子。

#### 3.4.7 与自动校准的分工

| | 自动校准（3.1） | 手动引导（3.4.3 + 3.4.4） |
| --- | --- | --- |
| 依赖的游戏元素 | 帮助图标、面板左右竖条、面板下边框、槽位方框 | 只有槽位方框 |
| 横纵缩放 | 相同 | 可以不同 |
| 用户操作 | 无 | 拖框、点一下 |
| 失败时 | 进入手动引导 | 提示重新对准 |

内置的帮助图标模板和面板边框坐标只服务于自动校准。即使游戏改版让它们全部失效，手动引导仍然可用，所以它们不是硬依赖。

## 4. 刷新状态机（RefreshEngine）

```
Idle ──start(recipe)──► Calibrating ──失败──► Paused(CALIBRATION_FAILED)
                            │成功
                            ▼
              ┌──────► Capture ──► Recognize ──► Decide
              │                                   │
              │   UNCERTAIN（< N 次）：不点击，重新截图
              │   MISS：Tap ──► 等待画面变化 ──┘
              │   HIT ──────────────────────────► Hit（震动，展开悬浮窗）
              │
   resume ◄── Paused(reason) ◄── NOT_FACTOR_SCREEN / FACTOR_SCREEN_OFF（开关关闭）/ 切出游戏 /
                                 连续 N 次 UNCERTAIN / 点击无效 / 达到次数上限 / 用户暂停
   任意状态 ──stop──► Stopped
```

关键规则：

1. **节拍**：两次截图的间隔 = max(1000 / 用户频率, `capturer.minIntervalMs`)。无障碍截图的 `minIntervalMs` 先取 333，第 9 节第 5 步实测后修正。
2. **点击后必须确认画面变了再判定**。点击后截到的 4 个结果如果和点击前完全相同，说明游戏可能还没刷新这一帧，这时**只重新截图，不再点击**。否则可能出现「真正的新结果是命中，却被下一次点击刷掉」的情况。连续 3 次都相同才判定「点击无效」并暂停。
3. **UNCERTAIN 不点击**：见第 1.5 节。
4. **开关关闭**（`FACTOR_SCREEN_OFF`）：暂停，悬浮窗提示「请先打开挑战因子开关」。工具不替玩家拨开关，理由与「不负责导航到因子界面」相同：开关是房间设置，由玩家决定。玩家打开后点「继续」即可，不需要重新校准，因为帮助图标和面板边框在两种状态下完全相同。
   - ~~开关已打开、但 4 个槽位仍是问号：直接点一次刷新~~。**删除（2026-11-01）**：维护者确认开关打开时游戏会立刻刷新，这个状态不存在。开关开时出现问号按 `UNCERTAIN` 处理（第 3.3 节）。
   - 运行中开关被关掉：同样暂停并提示。
   - 玩家在暂停期间自己打开开关，游戏会顺带刷新一次。引擎恢复后从「截图 → 识别」开始，**先判断当前结果是否命中，再决定点不点**，这样不会刷掉开关打开时恰好出现的目标组合。
5. **前台检测**：无障碍服务监听 `TYPE_WINDOW_STATE_CHANGED` 事件。点击开始时记下当时的前台包名（玩家此时一定停在游戏里），之后前台包名一变就立即暂停，不再截图。忽略本应用自己和输入法的事件。这样不需要维护游戏各渠道版本的包名列表。截图判断出 `NOT_FACTOR_SCREEN` 是第二道保险。
6. **线程**：引擎跑在 `Dispatchers.Default` 上的协程里，识别不占主线程；状态通过 `StateFlow` 推给悬浮窗。
7. **统计**：已刷新次数、实际速度（最近 10 次的平均）、识别失败次数、期望次数（`ProbabilityCalculator`）。

`Decision` 的输入是 4 个 `SlotResult`，输出 HIT / MISS / UNCERTAIN（见第 3.2 节的展开规则）。它是纯函数，单独测试。

## 5. 悬浮窗

- 由 `KazeAccessibilityService` 用 `TYPE_ACCESSIBILITY_OVERLAY` 创建，**不需要悬浮窗权限，也不需要单独的悬浮窗服务**。代价是必须先开启无障碍服务才能看到悬浮窗，对本工具没有影响，因为不开无障碍也无法刷新。
- 形态：
  - **小球**：可拖动。
  - **面板**：选配方、设频率、开始。
  - **运行中**：缩成一个小胶囊（次数 / 速度 / 暂停按钮）。
  - **命中**：展开，显示 4 个因子图标和「继续刷」「完成」按钮。
- **避让**：校准后得到「禁区」= 标题 + 4 个槽位 + 刷新按钮的屏幕矩形（各外扩 24 dp）。运行时如果悬浮窗与禁区重叠，自动移到禁区外最近的屏幕边缘。原因有两个：`dispatchGesture` 的触摸会落到最上层窗口；无障碍截图可能把悬浮窗也截进去（待真机确认），盖住槽位就会识别失败。
- 刷新按钮的点击位置取循环箭头中心（参考坐标 (1377, 433)，由主力开发测得的箭头外框 x 1343..1411、y 399..467 算出，校准后换算）。箭头只是不能当锚点，点击位置不受影响。点击坐标在按钮范围内随机偏移 ±10 px，不是为了防检测，而是避免每次正好点在按钮边缘的同一个像素上。

## 7. Manifest 与无障碍配置

`AndroidManifest.xml`（在 `<application>` 内新增服务，在外面新增一条权限）：

```xml
<uses-permission android:name="android.permission.VIBRATE" />

<service
    android:name=".service.KazeAccessibilityService"
    android:exported="true"
    android:label="@string/a11y_service_label"
    android:permission="android.permission.BIND_ACCESSIBILITY_SERVICE">
    <intent-filter>
        <action android:name="android.accessibilityservice.AccessibilityService" />
    </intent-filter>
    <meta-data
        android:name="android.accessibilityservice"
        android:resource="@xml/accessibility_service_config" />
</service>
```

- `BIND_ACCESSIBILITY_SERVICE` 保证只有系统能绑定这个服务；`exported="true"` 是系统绑定所必需的，有这条权限保护，其他应用调不了。
- `VIBRATE` 是普通权限，安装时自动授予，不弹窗。

新建 `res/xml/accessibility_service_config.xml`：

```xml
<accessibility-service xmlns:android="http://schemas.android.com/apk/res/android"
    android:description="@string/a11y_service_description"
    android:accessibilityEventTypes="typeWindowStateChanged"
    android:accessibilityFeedbackType="feedbackGeneric"
    android:accessibilityFlags="flagDefault"
    android:notificationTimeout="100"
    android:canRetrieveWindowContent="false"
    android:canPerformGestures="true"
    android:canTakeScreenshot="true" />
```

| 属性 | 用途 |
| --- | --- |
| `accessibilityEventTypes="typeWindowStateChanged"` | 只接收「前台窗口切换」事件，用于前台检测。不监听其他事件，耗电和隐私影响都最小 |
| `canRetrieveWindowContent="false"` | 不读取界面控件树（Unity 游戏里也读不到因子）。如果真机上发现事件里拿不到包名，再改成 `true` |
| `canPerformGestures="true"` | 允许 `dispatchGesture` 点击 |
| `canTakeScreenshot="true"` | 允许 `takeScreenshot`，Android 11 以下系统会忽略这个属性 |

`strings.xml` 新增 `a11y_service_label`（例如「KazeFactor 自动刷新」）和 `a11y_service_description`。描述要写明：只在玩家点击开始后截取屏幕并点击刷新按钮，截图只在内存中处理，不保存（「保存当前画面」按钮除外），不联网。

**不需要**的权限：悬浮窗权限 `SYSTEM_ALERT_WINDOW`、前台服务、通知权限。如果以后做第 9 节第 7 步的高速模式，再加 `FOREGROUND_SERVICE`、`FOREGROUND_SERVICE_MEDIA_PROJECTION` 和一个 `foregroundServiceType="mediaProjection"` 的服务。

**权限引导页必须处理的两个情况：**

1. **Android 13 起的「受限设置」**：从浏览器或文件管理器安装的 APK（也就是从 GitHub 下载安装的用户），系统默认不让开启无障碍服务，开关是灰的。用户要先到「应用信息 → 右上角菜单 → 允许受限设置」。本项目通过 GitHub 和 B 站分发，几乎所有用户都会遇到，引导页要放一个直达应用信息页的按钮，并配图说明。
2. **国产系统后台限制**：部分系统会在后台杀掉无障碍服务，表现为服务开关自己关掉。引导页提示用户把本应用加入自启动或电池优化白名单。各品牌入口不同，只做文字提示，不做跳转适配。

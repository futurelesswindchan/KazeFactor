## 1. 目标

玩家手动进入《元气骑士》联机模式的「挑战因子」配置界面后，在悬浮窗里选好配方并点击开始。工具循环执行「截图 → 识别 4 个槽位 → 与配方比对 → 未命中则点击刷新」，命中时停下并提醒玩家。

本阶段交付的是这个循环本身。配方的增删改、口令码分享和规则校验都已完成，不在本次范围内。

## 3. 功能需求

### 3.1 识别

- 输入一张游戏截图，输出 4 个槽位的结果。每个槽位是一个因子 id（1~59），或者 UNKNOWN。
- 匹配度低于阈值时判为 UNKNOWN，不能硬猜。
- 已知的槽位规则可以用来缩小候选范围：第 1 槽只会出现恶性因子，第 4 槽只会出现良性因子，详见 `PROJECT_STATUS.md` 第 6 节和 `SlotConstraint`。
- 需要判断「当前画面是不是因子界面」。不是的话，循环要暂停。
- 需要考虑多分辨率：目前只有一台测试机，但发布后用户的设备分辨率各不相同。现有设想是用刷新按钮或骰子图标做校准，算出缩放比例，不依赖问号图标来定位。

### 3.2 比对

- 直接复用现有接口 `Recipe.matches(4 个 id)`。
- 4 个槽位里只要有一个是 UNKNOWN，这一轮就不判定命中，并计入「识别失败」次数。

### 3.3 自动操作

- 用 `dispatchGesture` 点击刷新按钮。
- 停止条件：
  - 命中配方：停止并提醒玩家（提醒方式待定，见第 5 节）。
  - 玩家手动暂停或停止。
  - 切出游戏，或者当前画面不是因子界面。
  - 连续识别失败达到 N 次（N 待定）。
- 状态机草案：IDLE → CALIBRATING → CAPTURE → RECOGNIZE → MATCH → TAP_REFRESH → COOLDOWN。刷新没有动画，所以不需要等画面稳定。

### 3.4 悬浮窗

- 用 Compose 挂到 WindowManager 上。
- 功能：选择配方、设置频率、开始 / 暂停 / 停止、显示状态（已刷新次数，以及现有 `ProbabilityCalculator` 算出的期望次数）。
- 运行时悬浮窗要缩小，并避开刷新按钮和 4 个槽位，否则会挡住截图或者拦截点击。

### 3.5 主应用

- 引导用户开启所需权限，例如无障碍服务和悬浮窗权限，具体取决于最终方案。
- 提供进入悬浮窗模式的入口。

## 5. 需要架构方拍板的问题

### 5.1 截图方案（最关键）

已知冲突：`AccessibilityService.takeScreenshot()` 需要 API 30 以上，而且系统对调用频率有限制，过去的估计是每秒约 3 次，**未经真机验证**。这和「最高 10 次/秒」的需求冲突。

可选方向：

- **只用无障碍截图**：权限流程最简单，但频率有上限，还要求 minSdk ≥ 30 才能用这个功能（当前 minSdk 是 26）。
- **只用 MediaProjection**：频率高。但每次开始录屏都要用户同意，新版 Android 对这个授权的限制越来越多，还必须启动类型为 `mediaProjection` 的前台服务。
- **默认用无障碍截图，需要高频时切换到 MediaProjection**：这是现在的设想，但两条路径都要维护。

请决定：用哪种方案，频率上限要不要按方案下调，以及 minSdk 要不要调整。

### 5.2 识别技术

- 选 OpenCV 模板匹配，还是更轻量的方案（比如自己写缩放比对、感知哈希、颜色直方图）？
- 如果用 OpenCV：选哪个 Maven 制品和版本，APK 要不要按 ABI 拆分（native 库体积比较大），以及在 `core-domain` 的 JVM 单元测试里怎么跑识别。
- 识别模板来源：从实机截图里裁出来，还是用图标原图？这个决定也会决定 `assets/factors/icons/` 的去留。

### 5.3 模块边界

- 识别算法放在哪里：放进 `core-domain`（纯 JVM，可以用截图离线测试），新建模块，还是放在 `app`？
- 截图、识别、点击、状态机分别用什么接口隔开，好让识别逻辑能在没有设备的情况下测试？

### 5.4 测试策略

- 47 张截图怎么用：JVM 单元测试，还是 androidTest 仪器测试？
- 正确答案（每张截图的 4 个因子 id）由谁、用什么格式标注？

### 5.5 交互细节

- 命中时用什么方式提醒：震动、声音、通知，还是只在悬浮窗里显示？
- 连续识别失败多少次（N）后暂停？
- 要不要设置一个总刷新次数上限，防止配方概率很低时一直刷下去？
